\chapter{Results and Discussions}
This chapter presents the IRIS web application, highlighting its key features and user interfaces. The system demonstrates functionalities such as authentication with role-based access control, application creation and management, notifications, dashboards, and access to IP application documents and guides. Screenshots illustrate the perspectives of Technology Generators, TTBDO admins, UP officials, and Guests, showing both view-only and full management capabilities, as well as the workflow of starting and tracking IP right applications.

\section{System}

\subsection{Authentication}
The IRIS system handles user access through Google-based authentication and protected routing for role-based access control (RBAC). Registered users can access only the pages and functions permitted for their assigned role. Users within the UP system are required to use their UP Mail account, while users outside the UP system may use any valid Gmail account.

\subsubsection{Registered Users}
Registered users can sign in only if their Google email is already recorded in the system. After successful authentication, the system redirects the user to the homepage associated with their assigned role.

\subsubsection{Unregistered Users}
Unregistered users may gain access to IRIS through two pathways. First, a user may submit a sign-up request, which is reviewed by administrators through the user registration requests table. Second, an administrator may directly invite a user from within the system.

Once the administrator approves a request or sends an invitation, the user receives an email containing an invite link. This link is valid for 24 hours. After opening the invite link, the user is directed to the welcome page and then redirected to the homepage associated with their assigned role. This process is shown in \figref{fig:signup}, \figref{fig:invite_user}, \figref{fig:email_invite_link}, and \figref{fig:welcome_page}.

\subsubsection{Technology Generator Status Update Request}
Technology generators can request a status update when the current application status exceeds either the expected processing period based on the TTBDO citizen charter or the deadline set by the administrator. In IRIS, each application stage is represented by a flow identifier, while the current status represents the specific step of the application within that stage.

This feature provides technology generators with a formal way to follow up delayed applications. After a request is submitted, TTBDO admins can view the request through the system's request update notification and listing features, which are discussed in Section~\ref{sec:status_update_requests}.

\subsubsection{TTBDO Admin Application Collaborators View}
As shown in \figref{fig:admin_view_collaboratorsA}, the TTBDO admin has a similar view to the technology generator; however, instead of filing reports, the admin can only view reports filed against collaborators. 
The admin can also accept or reject requests for addition of a collaborator, when a technology generator would add a collaborator in an ongoing application as shown previously in \figref{fig:techgen_view_collaboratorsB}.
Since it is possible that not all collaborators of the IP have IRIS accounts, the co-applicants can be listed as plain text upon the start of the application, and then the TTBDO admin can link their accounts if they have one in the system later on, as shown in \figref{fig:admin_view_collaboratorsB}.
To make the system more forgiving for users that mistakenly forgot to list a collaborator, the system allows adding of collaborators even after the application has been started as shown in \figref{fig:admin_view_collaboratorsC}.
This is a feature that is not available for technology generators, as they can only link collaborators to the application, but cannot add new collaborators to the application.

In certain cases where a collaborator has been reported, the TTBDO admin has various options in how they would handle the report as shown in \figref{fig:admin_view_collaboratorsD}.
The TTBDO admin can use IRIS to send an email to all collaborators, except the one being reported, to initiate a meeting for further discussion of the conflict. 
If the conflict is resolved, the admin can then reflect the resolution in the system by resolving the report filed.
If the conflict is not resolved, the admin can remove the collaborator from the system, which also removes them from the list of collaborators of the application. 
It is important to note that a collaborator can only be removed if they have an unresolved report filed against them.

\subsection{Status Update Requests}
\label{sec:status_update_requests}
The Status Update Requests feature allows TTBDO admins to view and manage follow-up requests submitted by technology generators. A request is created when a technology generator follows up an overdue application status from the specific application page.

Once submitted, the request appears in the admin notification dropdown and in the complete list of status update requests. The dropdown provides immediate visibility of new requests, while the full requests page allows administrators to review all submitted follow-ups. Administrators may acknowledge a request after checking the related application. This helps ensure that overdue application steps are brought to the attention of the TTBDO admin.

\subsection{Start an Application}
IRIS enables technology generators to start their IP right application through the system. 
For cases where all collaborators of the IP right application do not have IRIS accounts, the admin can start the application on behalf of the technology generator, and then link the technology generator to the application later on when they have an account in the system.
It is important that the system allows admins to create applications so that these can be tracked in the system, even if the technology generators do not use the system.


\subsubsection{Application Wizard}
Since not all technology generators are familiar with the IP application process, as mentioned by the IP officer, the system provides a simple application wizard to guide them in choosing the right disclosure form to start their application as shown in \figref{fig:new_application}.
Technology generators can also choose to skip the wizard entirely, as some technology generators already know what disclosure forms to use. 
This page allows users to begin their IP right application.

\subsection{Notifications}
IRIS includes a notification component for technology generators and TTBDO admins. The system sends notifications when relevant changes occur in an application, such as attachment submissions, status updates, title updates, and application stage changes. Technology generators receive notifications related to their applications, while TTBDO admins receive notifications for relevant application activities.

The notification dropdown appears when an authenticated user selects the bell icon on the top bar. It displays recent notifications in chronological order, with the most recent notification shown first, as shown in \figref{fig:notification}.

\subsection{Dashboard}
The Dashboard page provides summary reports and visual representations of IP application data in IRIS. The dashboard view differs depending on the user's role.

For guests, administrators, and UP officials, the dashboard presents an overall IP portfolio overview. Users can select a reporting period, filter the displayed results by year range, and export the report as a PDF file. The dashboard includes the grant rate, portfolio status overview, charts showing application distributions and yearly trends by status, non-grant outcomes, and a summary table for the selected reporting period.

\subsection{Penetration Testing}

The penetration testing results showed that IRIS generally enforced its baseline security controls. Unauthenticated users were redirected from protected routes such as \texttt{/admin}, \texttt{/up-official}, \texttt{/techgen}, and direct application views. Non-admin users were also prevented from directly accessing administrator routes. The external users API rejected missing, invalid, and malformed bearer tokens, while unsupported POST, PUT, and DELETE requests were rejected. Direct REST access to sensitive tables, including users and IPR applications, did not expose private records. SQL-like, XSS-like, and path traversal-like payloads also did not produce observable data leakage or internal error disclosure.

\subsection{User Acceptance Testing}

User Acceptance Testing was conducted to determine whether the completed IRIS web application was acceptable to the team and client-side evaluators. During the testing, TTBDO participants evaluated the system from both administrative and Technology Generator perspectives. Some TTBDO personnel also acted as Technology Generators during testing, which allowed the team to observe how the system supported both office-side management tasks and user-side application activities.

The testing showed that the system was accepted after the main workflows were reviewed. The accepted workflows included role-based authentication and access, user and role management, application submission and monitoring, Technology Generator management, application registry visibility, notifications, reports, application documents, and dashboards. No major defect was identified that required a redesign of the system or prevented the use of its core functions.

The feedback gathered during UAT mainly consisted of refinements to existing features and additional office-specific requirements. Some of these refinements were already incorporated during continued system development and are reflected in the implemented modules discussed in the preceding sections. The remaining items were treated as enhancement recommendations because they did not prevent the use of the core workflows. The feedback covered the following areas:

\begin{itemize}
    \item interface and navigation improvements, including page layout, sidebar navigation, signup page display, and dashboard actions;
    \item user and role management refinements, such as role editing before approval, adding new users, and providing reasons for rejection;
    \item application workflow adjustments, including Technology Generator search, funding source selection, TTBDO email information, and IPOPHL IP number format validation;
    \item Technology Generator coordination controls, such as administrator approval when adding Technology Generators, notes for removal or reporting, and notifications to affected users;
    \item registry, public page visibility, and document management changes, including registry column revisions, public visibility rules, help links, and administrator-managed documents and forms; and
    \item report formatting revisions, including UPV branding, selected date range, yearly breakdown, removal of the CSV button, and display of a message when no chart is available.
\end{itemize}

One issue encountered during UAT involved the email invite link. The issue was traced to limitations of Supabase as the email delivery provider rather than to a failure in the system workflow itself. Since the invite workflow remained valid but the email delivery service was limited, the team decided to use a different email provider for sending invite links.

Overall, the UAT results showed that IRIS was acceptable for its intended use. The system’s main workflows were validated, while the feedback primarily focused on usability improvements, operational completeness, reporting details, and office-specific requirements. These results supported the completion of final refinements and helped identify enhancement items for continued system improvement.
