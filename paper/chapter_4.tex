\chapter{Results and Discussion}
This chapter presents the IRIS web application, highlighting its key features and user interfaces. The system demonstrates functionalities such as authentication with role-based access control, application creation and management, notifications, dashboards, and access to IP application documents and guides. Screenshots illustrate the perspectives of Technology Generators, TTBDO admins, UP officials, and Guests, showing both view-only and full management capabilities, as well as the workflow of starting and tracking IP right applications.

\section{System}

\subsection{Authentication}
The IRIS system handles user access through Google-based authentication and protected routing for role-based access control (RBAC). Registered users can access only the pages and functions permitted for their assigned role. Users within the UP system are required to use their UP Mail account, while users outside the UP system may use any valid Gmail account.

\subsubsection{Registered Users}
Registered users can sign in only if their Google email is already recorded in the system. After successful authentication, the system redirects the user to the homepage associated with their assigned role.

\subsubsection{Unregistered Users}
Unregistered users may gain access to IRIS through two pathways. First, a user may submit a sign-up request, which is reviewed by administrators through the user registration requests table. Second, an administrator may directly invite a user from within the system.

Once the administrator approves a request or sends an invitation, the user receives an email containing an invite link. This link is valid for 24 hours. After opening the invite link, the user is directed to the welcome page and then redirected to the homepage associated with their assigned role. This process is shown in \figref{fig:signup}, \figref{fig:invite_user}, \figref{fig:email_invite_link}, and \figref{fig:welcome_page}.

This feature provides technology generators with a formal way to follow up delayed applications. After a request is submitted, TTBDO admins can view the request through the system's request update notification and listing features, which are discussed in Section~\ref{sec:status_update_requests}.

\subsection{Start an Application}
The IRIS enables technology generators to start their IP right application through the system. 
For cases that all collaborators of the IP right application do not have IRIS accounts, the admin can start the application on behalf of the technology generator, and then link the technology generator to the application later on when they have an account in the system.
It is important that the system allows admins to create applications so that these can be tracked in the system, even if the technology generators would not use the system.

\subsection{Application Registry}
The Application Registry provides users with a quick overview of all IPs, allowing them to easily browse and reference relevant information. 
The registry is similar across user roles as seen in \figref{fig:registry}, but there are certain differences based on user roles. 
\figref{fig:registry_techgen} shows that the technology generators can only see the applications that they are involved in. They also have an action button to view the details of each application in their registry.
On the other hand, admins have total access, as illustrated in \figref{fig:registry_admin}, to all the IP portfolio of the system. Aside from viewing the details of each application, they can archive an application which hides the application from the registry but does not delete it from the system. 
It is important to note that archived applications are not counted in the system's metrics, ensuring that the data reflects only active applications. 

Guests and UP Officials have a similar view of the registry which is a read-only access, as shown in \figref{fig:registry_guest_official}. 
Guests can only see public applications while UP Officials can see all applications in the portfolio.

\subsubsection{Application Registry Filters and Sorting}
The application registry includes a filtering system that allows users to easily find specific applications based on various criteria as shown in \figref{fig:registry_filters}.
The filters include status, IP type, college names, names of technology generators, IP title, and project title.
The filters are available for all user roles, however, the guests cannot filter by status as this information is not available to them. 
On top of that, the application registry also supports sorting functionality to help users organize and prioritize their search results.
The sorting options include sorting by filing date, IP title, registration date, date added, and date.

\subsection{Application Documents}
The Application Documents page provides a centralized location for users to view the relevant IP disclosure forms for each IP type. This page can be viewed by both guests and technology generators. Through this page, users can identify the required forms and documents needed for the IP application process.

The page also includes a start application call-to-action button. When selected by a guest, the button redirects the user to the sign-in page. When selected by a technology generator, the button redirects the user to the new application page.

\subsection{Interoperability}
IRIS has the capability to integrate with external systems, for cases such as integration with the entire UP system. 
To demonstrate this capability, IRIS was integrated with an API endpoint that provides the list of users in the system.
The API endpoint is a mock endpoint that was created for testing purposes, and it returns a list of users in JSON format.
The endpoint can only be accessed through an API key that can be generated by admins as shown in \figref{fig:api_key_generation}.

\begin{figure}[H]                
    \centering 
    \includegraphics[scale=0.3]{interoperability/interoperability_API_key_generation.png}     
    \caption[API Key Generation]{API Key Generation. The admin interface for generating API keys which allow external systems to access IRIS' API.}
    \label{fig:api_key_generation}
\end{figure}

A local web app was created to demonstrate the integration with the API endpoint. 
The web app acted as a dummy external system that sent a request to the API endpoint with the generated API key. 
As shown in \figref{fig:api_integration}, the dummy external system successfully fetched data from IRIS which clearly demonstrated the interoperability of IRIS with external systems.

\begin{figure}[H]                
    \centering 
    \includegraphics[width=\textwidth]{interoperability/interoperability_external_system.png}     
    \caption[API Integration Demonstration]{API Integration Demonstration. A local web app that demonstrates the integration with the API endpoint by sending a request with the generated API key and displaying the list of users returned by the endpoint.}
    \label{fig:api_integration}
\end{figure}
