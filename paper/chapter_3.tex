\section{Research Design}

\subsection{System Development Life Cycle Model}
The study employed the Agile Software Development Life Cycle model, guided by the Agile Manifesto, which emphasizes responding to change and collaborating with customers (Beck et. al., 2001). These principles made Agile suitable for the development of IRIS because the system required continuous refinement based on the workflows of the Technology Transfer and Business Development Office (TTBDO), Technology Generators, UP Officials, and public users. Through incremental sprints, the researchers developed, reviewed, and improved core system modules such as authentication, application tracking, dashboards, document access, notification handling, user management, audit logging, and interoperability features.

However, certain limitations in using Agile were also acknowledged. Iterative feedback could cause ongoing expansion of requirements, which was mitigated by maintaining clearly defined functional and non-functional requirements, prioritized backlogs, structured sprint goals, and careful decision-making before adding new requirements. Additionally, heavy reliance on stakeholder input could result in delays in the development process. This was mitigated through scheduled progress updates and predetermined feedback windows. In the absence of timely input, development proceeded according to the approved requirements baseline.

Additionally, to help address these limitations, the developers used the Kanban board feature of GitHub Projects to manage the product backlog and monitor sprint progress. The board was organized into four columns: Backlog, In Progress, For Reviewing, and Done. Tasks were assigned to developers and updated accordingly as work progressed. The Scrum process was adapted into three-week sprint cycles to provide sufficient time for implementation, review, and feedback integration. At the end of each sprint, feedback was gathered from either the TTBDO or the research advisers. This feedback was translated into new tasks or refinements in the GitHub Projects board, allowing the developers to implement new features, improve existing functionalities, and address issues identified during review.

\subsection{Research Framework}
The research framework followed a systematic progression from problem identification, requirements analysis, system design, development, and evaluation.

The research began by identifying the limitations of the existing IP application monitoring and document tracking process within the university. These limitations were identified through interviews with TTBDO personnel and observation of existing workflows. Concurrently, a review of local and international literature on IP management systems, university technology transfer, digital records management, and role-based access control was conducted to establish the conceptual foundation for the system design.

Building on these insights, system requirements were elicited and analyzed through user interviews and document analysis. The requirements were organized according to the system's major users, namely Technology Generators, TTBDO Admins, UP Officials, and Guests. These requirements were then translated into system features through iterative Agile development cycles. Continuous feedback from stakeholders was gathered to ensure that the system reflected actual IP application workflows, including application creation, application monitoring, status updating, document access, user registration, notification delivery, dashboard reporting, and controlled data sharing through an API endpoint.

Finally, the system was evaluated through the testing activities described in Section~\ref{sec:testing_and_evaluation}, Testing and Evaluation. The feedback and test results gathered during this phase informed final system adjustments before deployment.

\section{Requirements Analysis}

\subsection{Data Collection Methods}

Data was gathered through multiple methods to ensure an accurate understanding of existing processes:

\begin{itemize}
  \item Interviews: Conducted with TTBDO personnel to identify workflow challenges, user roles, access levels, and document handling needs.
  \item Observation: Reviewed the current manual document tracking, IP filing, and application monitoring process.
  \item Document Analysis: Examined sample forms, tracking logs, IP disclosure forms, process documents, and application flow references.
\end{itemize}

\subsection{Functional Requirements}

The functional requirements (FRs) of IRIS defined the baseline system capabilities needed to address the inefficiencies of TTBDO's manual intellectual property management process. These requirements translated the project objectives into general system functions and served as the basis for the design and implementation of the system. They were organized into the following functional areas: authentication and role-based access, IP application management, application tracking and registry, document and attachment management, collaborator management, notifications and reminders, dashboards and reporting, audit trail and accountability, public portal, and interoperability.

For authentication and role-based access, IRIS required users to authenticate before accessing internal system features. The system supported role-based access control for Technology Generators, TTBDO Admins, UP Officials, and Guests. Each role was provided access only to the functions and information appropriate to its responsibilities. The system also supported user access management through registration approval, invitation, and role assignment.

For IP application management, IRIS allowed authorized users to create and manage intellectual property application records. The system supported the submission and monitoring of different IP application types, including Trademark, Utility Model, Industrial Design, Patent, and Copyright. It also provided mechanisms for entering application details, identifying collaborators, uploading supporting files, and reviewing application information.

The application tracking and registry requirements focused on maintaining a centralized record of IP applications. The system allowed authorized users to search, filter, sort, and view application records based on their role permissions. It also allowed users to monitor the current status, progress, timestamps, and relevant updates associated with each application.

For document and attachment management, IRIS allowed authorized users to upload, access, and update supporting documents associated with IP applications. The system maintained records of document updates to support traceability and enforced role-based access restrictions for application documents and attachments. It also provided access to relevant application forms, guides, and reference documents.

The collaborator management requirements enabled authorized users to associate collaborators with IP applications and view collaborator information linked to each record. The system also provided mechanisms for managing collaborator-related concerns, including reporting or reviewing collaborator issues when necessary.

For notifications and reminders, IRIS provided system notifications for relevant application updates, status changes, document-related actions, and time-sensitive activities. The system also supported reminders for application deadlines and maintained a notification history for users.
The automated deadline notifications are both sent through email and displayed in the system's notification center, ensuring that users receive timely reminders about upcoming deadlines and can take necessary actions to avoid overdue applications.

Dashboards and reporting enabled users to view summaries of application statistics, trends, and status distributions according to their access level. The system also supported report generation and export functions for monitoring, administrative review, and decision-making.

The audit trail and accountability requirements ensured that relevant user and system actions were recorded for traceability. These records supported the review of system activities, including actions performed, timestamps, outcomes, and related changes.

The public portal provided read-only access to published intellectual property information and selected public-facing resources. Guests could view public application information, summary statistics, application documents, and guidance materials without accessing restricted internal functions.

Finally, the interoperability requirements allowed controlled data exchange with external systems through an authorized mechanism. Access to external data sharing features was restricted through appropriate authentication or authorization controls.

The complete set of baseline functional requirements is provided in Appendix~\ref{sec:appendixa}.

\subsection{Non-Functional Requirements}

Non-functional requirements (NFRs) defined the standards that IRIS needed to meet for performance, security, usability, maintainability, interoperability, and compliance, while also supporting stable and consistent system behavior during use. NFRs were critical for a system that handled sensitive IP data, served users with different access privileges, and maintained public trust through controlled availability and consistent system behavior.

In terms of performance, IRIS was designed to provide responsive access to application records, dashboards, registry searches, and file-related actions under normal usage conditions. For security, the system enforced role-based access control, protected routing, authenticated access to internal features, and controlled access to application files and administrative functions. Supabase supported the system's authentication, database security, and access control mechanisms.

Regarding system stability and availability, IRIS was designed to maintain dependable access to core features such as authentication, application tracking, dashboards, notifications, and document viewing. Usability and accessibility considerations included a responsive web interface for desktop users, consistent navigation patterns, meaningful feedback messages, confirmation dialogs for critical actions, and role-appropriate interface layouts.

For maintainability, portability, and scalability, the system followed a modular web application structure with separation of concerns across pages, components, database operations, and service logic. The system also included API-based interoperability to demonstrate how IRIS could exchange controlled data with an external system through an API key.

Finally, IRIS adhered to the Philippine Data Privacy Act of 2012 by limiting access to sensitive records according to user roles and by supporting accountability through audit logs and controlled data access. It also supported records management by maintaining application histories, attachment version histories, status histories, and exportable information for reporting.

Appendix~\ref{sec:appendixb} (Tables~\ref{tab:nfr_performance}--\ref{tab:nfr_compliance}) provides the complete set of non-functional requirements. The main text above summarizes the mandatory requirements, while additional SHOULD and MAY requirements are included in the appendix.

\subsubsection{TTBDO Admin}
The TTBDO Admins are the primary administrative users of the system. They have full access to the management features of IRIS, including user management, registration request approval, application creation, application status updating, deadline management, attachment handling, collaborator linking, collaborator report review, application withdrawal, dashboard reporting, audit trail viewing, and API key generation. They can also view and manage the full IP portfolio of the university.

\subsubsection{Technology Generators}

Technology Generators, or university researchers and IPR applicants, primarily use the system to start IP right applications and monitor applications connected to them. They can access the application documents and application guide, create new applications, view application status histories, upload and update attachments, view attachment version history, link collaborators, report collaborators to TTBDO Admins, receive notifications, and request a status update when a deadline on an application is overdue. They can also view public and role-appropriate dashboard and registry information.

\subsubsection{UP Officials}

UP Officials have view-only access to the university IP portfolio. Unlike Guests, they can view all applications in the registry regardless of public status. They can also use dashboard summaries, and view, filter, and sort the university's IP portfolio for evaluation.

\subsubsection{Guests}

Guests are unauthenticated or public users with limited access. They can view public applications in the registry, access public dashboard information, open application documents, read the application guide, and submit a registration request when they need access to internal system functions.

\section{Testing and Evaluation}\label{sec:testing_and_evaluation}

\subsection{Testing Approach}

The system underwent End-to-End Testing, Performance Testing, Penetration Testing, and User Acceptance Testing (UAT) to validate functional and non-functional requirements (FRs and NFRs, listed in Appendix~\ref{sec:appendixa} and \ref{sec:appendixb}).

\FloatBarrier

\subsection{End-to-End Testing}

The Playwright Test framework was used to automate the end-to-end tests of the system. 
The tests were written to simulate real-life use-case scenarios, and the diagrams from section \ref{sec:us_diagram} were used as a foundation to derive the tests; as such, 31 use-case tests were identified. 
The tests were divided by user roles, and another group of tests was created to verify that users can access only the routes they are allowed to as described by the authentication FR (FR-01). 
The tests were defined as followed:

\begin{itemize}
    \item \textbf{Technology Generator}
    \begin{itemize}
        \item Shows the techgen dashboard updates and summary cards.
        \item Filters the registry and opens an application from the results.
        \item Shows application details, collaborator states, owned files, and version history.
        \item Lets a techgen request a status update when an application is overdue.
        \item Files a collaborator report only after confirmation.
        \item Auto-links an unverified collaborator after confirmation.
        \item Views an existing file and uploads a new attachment through the modal flow.
        \item Uploads a new file version instead of replacing the existing one.
        \item Creates a new application after confirmation and keeps collaborators visible in the detail page.
        \item Shows techgen notifications and lets the user clear unread reminders.
    \end{itemize}

    \item \textbf{TTBDO Admin}
    \begin{itemize}
        \item Manages dashboard exports, year filters, and status update requests.
        \item Handles attachment actions and links tech generator accounts.
        \item Edits application details, updates status, and withdraws applications.
        \item Views collaborator reports and removes a tech generator.
        \item Invites a new user from user management.
        \item Approves user registration requests.
        \item Rejects user registration requests.
        \item Generates and copies an API token.
        \item Creates a new application from the registry through the guided wizard.
        \item Validates required start-application inputs and supports manual collaborators.
    \end{itemize}

    \item \textbf{Guest}
    \begin{itemize}
        \item Shows only public applications in the registry.
        \item Filters and sorts the public registry without exposing private applications.
        \item Lets guests request registration and validates UP mail signups.
    \end{itemize}

    \item \textbf{UP-Official}
    \begin{itemize}
        \item Shows the dashboard for evaluating the university IP portfolio.
        \item Shows all applications in the registry regardless of public status.
        \item Filters registry results.
        \item Sorts the registry alphabetically by IP title.
    \end{itemize}

    \item \textbf{Routing}
    \begin{itemize}
        \item Redirects unauthenticated users away from protected pages.
        \item Keeps admins inside admin routes.
        \item Keeps techgens inside techgen routes.
        \item Keeps UP officials inside up-official routes.
    \end{itemize}
\end{itemize}

\FloatBarrier

\subsection{Performance Testing}

Performance testing was conducted to evaluate the loading speed, responsiveness, and visual stability of the IRIS web application. The test was included to determine whether public and authenticated pages could load reliably under the tested conditions.

The testing was performed using Lighthouse audits on selected routes. The routes were grouped into public pages, TTBDO Administrator pages, Technology Generator pages, and UP Official pages. Public routes were tested without authentication, while authenticated routes were tested using browser sessions configured for the corresponding user roles.

The Lighthouse audits recorded the performance score, tested route, device mode, final loaded path, redirect status, and validity of the test. The key metrics recorded were First Contentful Paint, Largest Contentful Paint, Total Blocking Time, Cumulative Layout Shift, and Speed Index.

The performance testing covered the following route groups:

\begin{itemize}
    \item public pages, including the landing page, sign-in page, sign-up page, application registry, application documents, application guide, and welcome page;
    \item administrator pages, including the dashboard, application registry, audit trail, developer settings, user management, notifications, pings, application creation, and application viewing pages;
    \item Technology Generator pages, including the dashboard, application registry, application documents, application guide, notifications, application creation, and application viewing pages; and
    \item UP Official pages, including the dashboard and application registry.
\end{itemize}

The results were used to identify whether the tested routes were responsive and stable, and whether any pages required further performance optimization.

\subsection{Penetration Testing}

Penetration testing was conducted to evaluate the baseline security controls of the IRIS web application before final deployment. The test focused on common security concerns, including unauthorized access, improper role use, exposed database resources, unsafe API access, suspicious input handling, and error-message leakage.

The testing was performed using a scripted set of HTTP requests against the locally deployed instance of IRIS and its connected Supabase backend, as shown in Appendix~\ref{appendix:penetration-testing-script}. The requests simulated unauthenticated users, authenticated users with different roles, invalid bearer tokens, unsupported HTTP methods, direct REST access attempts, suspicious input payloads, and user-supplied role tampering. Each test case recorded the tested area, expected secure behavior, observed response, result, and evidence file.

\subsection{User Acceptance Testing}

User Acceptance Testing (UAT) was conducted to validate whether the IRIS web application matched the workflow expectations and operational needs of the TTBDO. The activity involved the development team and TTBDO client-side evaluators. Some TTBDO participants also acted as Technology Generators so that the system could be reviewed from both administrative and end-user perspectives.

The UAT was conducted through a walkthrough and validation of the deployed system. Participants reviewed the main workflows, including authentication and invite-based access, user and role management, application submission and viewing, Technology Generator management, application registry, public pages, notifications, reports, documents, dashboards, and general interface navigation. Feedback was recorded according to the affected module and used to identify accepted functions, minor refinements, and limitations caused by external services.

This activity was included because internal testing only verified the technical correctness of the system, while UAT validated whether the system was practical, usable, and acceptable in the intended office setting. The system was considered acceptable when the core workflows functioned as intended, no critical issue prevented use, and the remaining concerns were limited to refinements or additional office-specific requirements.

\subsection{Evaluation Criteria}

The system was evaluated based on criteria aligned with the testing activities conducted for the project. These criteria were used to determine whether the system was functional, usable, secure, and suitable for the intended TTBDO workflow.

\begin{itemize}
  \item Functionality: The implemented modules operated according to the defined functional requirements and supported the intended user workflows.
  \item Usability and Acceptance: The system was considered acceptable if client-side evaluators were able to complete the main workflows and the remaining feedback consisted only of refinements or additional office-specific requests.
  \item Performance: The system was evaluated using Lighthouse performance metrics, including performance score, First Contentful Paint, Largest Contentful Paint, Total Blocking Time, Cumulative Layout Shift, and Speed Index.
  \item Security: The system was evaluated through scope penetration testing focused on authentication, role-based access control, API protection, database access control, input validation, and error handling.
  \item Reliability: The system was considered reliable if no critical errors prevented the completion of the tested workflows during validation.
\end{itemize}
