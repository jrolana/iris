\section{Research Design}

\subsection{System Development Life Cycle Model}
The study employs the Agile Software Development Life Cycle model, guided by the Agile Manifesto, which emphasizes responding to change and collaborating with customers (Beck et. al., 2001). These principles make Agile flexible and iterative, allowing continuous feedback from TTBDO personnel and early validation of system components. Through incremental sprints, the researchers were able to refine features based on actual user input.

However, certain limitations in using Agile are also acknowledged. Iterative feedback can cause ongoing expansion of requirements, which can be mitigated by maintaining clearly defined functional and non-functional requirements, prioritized backlogs, structured sprint goals, and thorough decision-making in adding more requirements. Additionally, heavy reliance on client input might result in delays in the development. This is mitigated through scheduled progress updates and predetermined feedback windows. In the absence of timely input, development proceeds according to the approved requirements baseline. 

Additionally, to help address these limitations, the developers used Jira to manage product backlog and structure sprint activities. In line with this, Saiyad (2024) found a 25\% increase in project completion rates among teams using Jira, highlighting the tool’s effectiveness in improving project management efficiency and team collaboration within Agile Scrum environments. 

\subsection{Research Framework}
The research framework follows a systematic progression from problem identification through system development to rigorous evaluation.

The research begins by identifying the limitations of the current manual IP tracking process within the university. These limitations were identified through interviews with TTBDO and observation of existing workflows. Concurrently, a review of local and international literature on IP management systems and best practices was also conducted to establish the conceptual foundation for the system design.

Building on these insights, system requirements were elicited and analyzed through user interviews and document analysis. These requirements, both functional and non-functional, were then organized and translated into system features through iterative Agile development cycles. Continuous feedback from stakeholders was gathered to ensure the system meets user needs and organizational workflows.

Finally, the system was evaluated using Performance, Security, and User Acceptance Testing (UAT) involving the four key user roles. Feedback gathered during this phase informed final system adjustments before deployment.

\section{Requirements Analysis}

\subsection{Data Collection Methods}

Data was gathered through multiple methods to ensure an accurate understanding of existing processes: 

\begin{itemize}
  \item Interviews: Conducted with TTBDO staff to identify workflow challenges. 
  \item Observation: Reviewed the current manual document tracking and IP filing process. 
  \item Document Analysis: Examined sample forms, tracking logs, and process documents.
\end{itemize}

\subsection{Functional Requirements}

The functional requirements (FRs) of IRIS defined the specific system behaviors, capabilities, and interactions that addressed the inefficiencies of TTBDO’s current manual IP management process. These requirements translated the project objectives into specific system behaviors and are organized into seven key functional areas namely: authentication, application submission, application tracking, dashboards, notifications, document management, and public access. 

For authentication, the system requires all users to authenticate before accessing internal features and implements role-based access control. In the submission of applications, IRIS guides users in selecting the IDFs by IP type and enables review of IP-related documents. The system also logs timestamps whenever application statuses are updated.

The application tracking functionality maintains a registry of applicants and their submissions, allows authorized users to search and review submission histories, and supports filtered and faceted searches over the registry. Dashboards and reporting provides real-time statistics, trends, and breakdowns, with options to generate and export reports in both machine and human-readable formats.

In terms of notifications, the system sends in-app alerts for application status changes or approaching deadlines and maintain a notification history for each user. The deadline notifications are also automatically emailed to all collaborators and the admin, which follows three tiers: a week before the deadline, three days before, and on the deadline itself. The deadline for the annual fees of Patent and Trademark IP types are also automatically sent by the system, following the same notification schedule. The document management capabilities enables the TTBDO staff to upload and securely store supporting documents linked to application records, with access enforced according to user roles.

Finally, the public portal provides read-only access for guest users to browse published IPs, display summary statistics, and publicly available IDF documents.

The complete set of functional requirements, including all detailed specifications, is provided in Appendix~\ref{sec:appendixa} (Tables~\ref{tab:fr_auth_roles}--\ref{tab:fr_public_portal}).

\subsection{Non-Functional Requirements}

Non-functional requirements (NFRs) define the standards that IRIS must meet for performance, security, reliability, usability, maintainability, and compliance. NFRs are critical for a system handling sensitive IP data, serving diverse users with varying technical skills, and maintaining public trust through consistent availability.

In terms of performance, IRIS is expected to return 95\% of requests within two seconds under normal load and support at least 100 concurrent users. For security, the system will encrypt all traffic using TLS 1.2 or higher and enforce role-based access control. To meet this requirement, the system is built with Supabase framework, which has built-in authentication and access control features. Moreover, the Supabase framework protects all data with encryption of TLS 1.2+ and AES-256 for data at rest.

Regarding reliability and availability, IRIS is designed to achieve 99.5\% uptime during business hours, recover to the last stable state within four hours in case of failure, and perform daily backups stored in two separate locations. Usability and accessibility considerations include a responsive web interface for desktop, consistent UI and navigation patterns, meaningful error messages, and compliance with WCAG 2.1 Level AA accessibility standards. 

For maintainability, portability, and scalability, the system followed a modular design with separation of concerns, included API implementation for interoperability, and deployed to run across multiple environments.

Finally, IRIS adheres to the Philippine Data Privacy Act of 2012, retains records according to UP and IPOPHL retention policies, and can export logs and reports in standard formats. 

Appendix~\ref{sec:appendixb} (Tables~\ref{tab:nfr_performance}--\ref{tab:nfr_compliance}) provides the complete set of non-functional requirements. The main text above lists only mandatory SHALL requirements; additional SHOULD and MAY requirements are included in the appendix.

\subsubsection{TTBDO Admin}
The TTBDO Admins are the key stakeholders of the system, and as such have full access to the functionalities of the system. It includes managing the accounts of the users, the documents relating to every IPR application, the IPR status and critical deadlines, as well as having a full overview of the entire IP portfolio of the university. They can also gather reports of the IP portfolio from the system, which they can later use for further IP-driven strategies and decisions. 

\subsubsection{Tech Generators}

The Tech Generators, or the university researchers and IPR applicants, have the primary interaction of overseeing the current status of the IPs related to them. That is, if they are a member of the tech generators of a certain IP. They can also access and file disclosure forms to start their IPR application. The Tech Generators are notified by the system every time there is a status change to their IPR, may it is in the process of applying or while maintaining their rights to it. Aside from this, they also have viewing privileges to the IP portfolio summary and the published IPs of the university.

\subsubsection{UP Officials and Guests.}

These stakeholders in the system only have viewing capabilities with the IP portfolio summary as well as the published IPs of the university. The UP officials, however, have extended privileges to have an overview of the unpublished IPs or the ongoing IPR applications.

\section{Testing and Evaluation}

\subsubsection{Testing Approach}

The system will undergo Performance Testing, Penetration Testing, and User Acceptance Testing to validate functional and non-functional requirements (FRs and NFRs, listed in Appendix~\ref{sec:appendixa} and \ref{sec:appendixb}).

Performance testing will evaluate system responsiveness and stability to validate NFR-01 (95\% of requests within 2 seconds). Testing will focus on application submission (FR-03 to FR-06), dashboard access (FR-10), and search functionality (FR-08 to FR-09), measuring page load times and response rates under normal usage conditions.

Penetration testing will validate FR-02 and NFR-04 (role-based access control). Tests will attempt unauthorized access to restricted functions by simulating users accessing features outside their assigned roles, such as Applicant users attempting to access TTBDO document upload functions (FR-15). Authentication (FR-01) will be tested by attempting access to protected routes without valid credentials. Input validation will be tested by submitting malicious or unexpected data to verify that security mechanisms properly sanitize inputs and prevent unauthorized access.

User Acceptance Testing will involve end-users from each role (TTBDO staff, applicants, UP officials) completing representative tasks: application submission and document review (FR-03 to FR-06), applicant tracking (FR-07 to FR-08), notifications (FR-12 to FR-14), and dashboard reporting (FR-10 to FR-11). The responsive interface (NFR-09) will be tested across desktop devices, and navigation consistency (NFR-10) will be assessed through user feedback on interface clarity and ease of use.

\subsubsection{Evaluation Criteria}

The evaluation of the system focuses on key aspects aligned with the Testing Approach to ensure overall effectiveness and readiness.

\begin{itemize}
  \item Functionality: All modules are operational and aligned with defined requirements. 
  \item Usability: Interface rated “very satisfactory” by evaluators. 
  \item Performance: Average page load time maintained under three seconds. 
  \item Reliability: No critical errors or crashes occurred during UAT. 
\end{itemize}
